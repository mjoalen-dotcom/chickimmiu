# 分類頁／商品頁 ISR 適用性評估｜步驟09（FE-QA Prompt H 第2項）

日期：2026-08-15｜依 Prompt H 要求，本項只給評估與建議，不逕自實作（庫存/價格屬購買決策相關資料，變動 revalidate 策略風險較高，留給 Alan 決策）。

## 現況

`src/app/(frontend)/category/[slug]/page.tsx` 與 `src/app/(frontend)/products/[slug]/page.tsx` 皆已明確設定 `export const dynamic = 'force-dynamic'`——**這是既有的刻意決定，不是遺漏**，每次請求都重新查庫存/價格，確保顯示絕對即時。

## Trade-off

| 方案 | 優點 | 缺點 |
|---|---|---|
| **維持 force-dynamic（現況）** | 庫存/價格 100% 即時，不會有「頁面顯示有貨、結帳才發現缺貨」的落差 | 每次請求都吃資料庫查詢成本，TTFB 隨流量線性變差 |
| **改 ISR revalidate:60** | 大幅降低資料庫負載，多數請求吃快取 | 最多 60 秒的庫存/價格顯示落差；熱銷商品搶購時，60 秒內庫存從有到無不會即時反映在頁面（結帳時仍會被 server-side 驗證擋下，不會超賣，只是「頁面看起來還有貨」體驗上不夠即時） |
| **混合：頁面殼 ISR + 庫存數字 client-side 補抓即時值** | 兼顧兩者，頁面骨架走快取，庫存/價格用小 API 請求即時補上 | 開發成本最高，需額外設計一支輕量庫存查詢端點 + client component，且會多一個 network round-trip |

## 建議

依 CKMU 現況（非搶購型秒殺為主、無限時限量倒數的商品線佔比不高）：**分類頁可以先改 ISR revalidate:60**——分類頁是瀏覽/導購頁面，庫存準確度要求本來就低於商品頁與結帳頁，60 秒的落差對使用者體感影響極小，換來的效能提升明確。**商品頁（PDP）建議維持 force-dynamic**——這是使用者做出「加入購物車」決策的最後一站，庫存顯示的信任度比效能更重要，且結帳流程本身已有 server-side 超賣防線兜底，即時顯示的價值大於效能損失。

若 Alan 認同上述方向，下次「下一步」（或另行指示）可以只改分類頁的 `dynamic` 為 `revalidate = 60`，商品頁維持原樣不動。本次評估未實作任何改動，兩個檔案皆保持 `force-dynamic` 不變。
