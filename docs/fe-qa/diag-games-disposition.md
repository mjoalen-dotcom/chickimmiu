# /diag 與 /games 用途確認與處置（FE-QA-001 Prompt I 項目1）

F4 原始判定：「/diag 與 /games 公開連結於首頁，上線前必須移除或加權限」。工作單風險表本身也已預留但書：「/diag /games 為團隊在用工具｜移除前先確認用途，改權限閘而非刪除」。實際查證後，兩者情況不同，且都不該直接移除或加權限閘。

## /diag — 客服診斷頁，非公開連結，維持現狀

`src/app/(frontend)/diag/page.tsx` 明確標註是「iPad / Safari 隱私診斷頁」：客服收到「iPad 白屏」回報時，請使用者手動輸入這個網址截圖回傳。內容只有瀏覽器能力偵測（localStorage／cookie／indexedDB 是否被封鎖）與 User-Agent，**不含任何機密或個資**。

全站程式碼搜尋確認：沒有任何導覽列、footer、選單連結到 `/diag`。唯一出現處是 `layout.tsx` 內建的「開機失敗兜底畫面」（`__ckmuBootRender`）——當 React 4 秒內沒有成功掛載時才會顯示，裡面有「前往診斷頁」的按鈕連結到 `/diag`。F4 判定的「首頁連結」推測是掃描原始 HTML 時，抓到這段內嵌在每頁 `<head>` 的 script 字串裡的 `href="/diag"` 文字（該 script 平時不會渲染出畫面，只在網站真的掛掉時才觸發）——不是實際會被使用者點到的公開連結，是誤判。

**處置**：不動。它是網站掛掉時唯一還能運作的求助管道之一，加權限閘反而會在最需要它的當下（使用者連正常頁面都打不開）多一道使用者過不去的關卡。也不需要移除連結，因為原本就沒有真正的公開連結存在。

## /games — 完整會員遊戲化功能，非測試頁，維持現狀

`/games` 不是除錯／測試頁，是一組已完整開發的會員遊戲化中心：排行榜、徽章、積分、每日簽到、MBTI 風格測驗、刮刮樂、卡牌對戰、藏寶圖。全站確認多處**刻意**導覽連結：footer（`Footer.tsx`）、右下角浮動選單（`FloatingQuickMenu.tsx`）、會員中心側欄（`account/layout.tsx`）、會員總覽頁（`account/page.tsx`）。這是既有正式功能，不是要收掉的東西。

**處置**：不動、不加權限閘。F4 對 /games 的判定不成立——推測是掃描時把它與 /diag 歸為同類「看起來像測試頁」的路由，實際未深入查看內容。

## 結論

Prompt I 項目1「/diag 與 /games：確認用途後，自 production build 移除路由，或加環境變數閘」——確認用途後，兩者皆判定不應移除或加閘，維持現狀是正確處置，非跳過此項目。
