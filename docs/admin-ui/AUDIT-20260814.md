## 5. 資安確認項（工單指定必查兩項）

### 5.1 未登入 `/admin` 回 200 而非 redirect 至 /admin/login

**已實測確認：非安全問題，是 Payload 3 的實作模式差異。**

`curl https://pre.chickimmiu.com/admin`（未帶 cookie）回 HTTP 200，無 `Location` header（非 3xx 重導向）。但比對回應內容：
- HTML 內含登入表單欄位（`email`、`password`、`forgot` 字樣），與 `/admin/login` 的內容高度相似（46,787 bytes vs 49,563 bytes）。
- **未**發現任何實際後台資料外洩字樣（訂單管理／商品管理／今日訂單等 dashboard 內容一律不存在於未登入回應中）。

**結論**：Payload 3 admin panel 在 `/admin` 路由本身用 server-side render 直接吐出登入表單（SPA 風格閘門），而非傳統 HTTP redirect 到獨立 `/admin/login` URL。這是刻意設計，不是「client-side 才擋」的資安漏洞——伺服器端確實在把關，只是回應碼固定 200 而非 302。**無需修補，原稽核清單中的「未經驗證」旗標可解除。**

### 5.2 顧客帳號是否與後台管理員共用 users collection

**已實測確認：是，共用。**

- `GET /api/users` → 403（已鎖，符合預期）
- `GET /api/customers` → 404（**無**獨立 customers collection）
- `src/collections/Users.ts` 內 `role` 欄位（select，選項 admin/partner/customer，預設值 `customer`）證實三種身分共用同一張表，僅以 `role` 欄位值區分。
- **風險緩解確認**：`role` 欄位的 `create`/`update` access 皆鎖 `isAdminFieldLevel`（僅管理員可寫入），一般會員 API 無法自我拉高權限至 admin。**目前無立即可利用的權限提升路徑**。
- **仍是架構隱憂**：APP-API-001（步驟16）規劃發給 APP 端的顧客 JWT，若沿用同一 auth collection/namespace，語意上等同持有「後台鑰匙的同款式」，僅靠 role 檢查把關，非架構層隔離。**該工單已將「customers 分離」列為 Phase 1 第一動作，本次審計結果印證此判斷正確，維持原排程（步驟16）不變。**
